# 模式一：项目初始化细则

为当前仓库初始化 AI 项目环境。目标：让后续任何 Agent 会话都能规避错误、快速上手。

## 目录

1. Step 1: 规则配置确认
2. Step 2: 编码规则落盘（CONTEXTS.md）
3. Step 3: 生成 AGENTS.md
   - 3.1 调研方式
   - 3.2 需要提取的内容
   - 3.3 提问规则
   - 3.4 编写规则
   - 3.5 需要排除的内容

## 1. Step 1: 规则配置确认 ⚠️ REQUIRED

告知操作者：miemou 已内置六套成员规则（完整原文在 `references/member-guidelines.md`，
架构配套见 `references/codebase-design.md` 与 `references/architecture-report.md`），
本项目与团队运行**无需安装外部 skill、无需在线获取规则**：

- **karpathy 四原则** — 行为准则，减少 LLM 常见编码失误（过度工程、臆测假设、缺乏验证标准），
  适用于所有代码编写、审查、重构场景
- **ponytail（最简完整改动）** — 强制最简可行方案，抑制过度工程，适用于所有编码任务与依赖选型
- **诊断循环** — 困难 bug 与性能回退的六阶段诊断（反馈回路 → 复现最小化 → 假设 → 插桩 →
  修复回归 → 清理），适用于功能异常、抛异常、运行缓慢的诊断
- **TDD** — 红-绿-重构循环，适用于团队要求测试先行或编写集成测试的场景
- **审视法** — 对计划/设计/决策的高压质询，适用于方案压测与决策验证
- **架构深化** — 扫描代码库深度优化机会（删除测试、浅模块信号），适用于架构优化与模块接口改进

(conditional) 操作者的 agent 环境支持独立 skill 安装且操作者明确想要时，才逐个确认安装。
安装原则：

- 不安装与项目技术栈无关的 skill
- 不安装功能重叠的 skill
- 安装失败不影响整体初始化流程，跳过即可

操作者不需要独立安装时，本步骤只需确认「内置规则已就位」，直接进 Step 2。

## 2. Step 2: 编码规则落盘（CONTEXTS.md）

取 `references/member-guidelines.md` §1 的 karpathy 四原则原文（含取舍说明与生效标志），
落到当前项目根目录 `CONTEXTS.md`——不绑定任何 agent 工具链的通用上下文文件。
与 Step 3 的 `AGENTS.md` 明确分工：`CONTEXTS.md` 承载编码行为基线（跨项目通用的行为准则），
`AGENTS.md` 只写本仓库专属指引（§3 的高价值提取物），互不掺杂：

- 文件不存在 → 直接创建，内容为四原则全文。
- 文件已存在 → 与现有内容**合并**：保留项目专属指令，去重冲突条款，不全盘重写、不丢弃既有内容。

该基线适用于所有代码编写场景，是后续会话与团队成员（子 agent）的行为底线。

## 3. Step 3: 生成 AGENTS.md ⚠️ REQUIRED

为当前仓库创建或更新 `AGENTS.md`。

目标：生成一份精简的指令文件，帮助 Agent 后续会话规避错误、快速上手。每一条内容都要回答
这个问题：「如果没有这份提示，AI Agent 是否很容易遗漏该信息？」答案是否定的，就不要写入。

必须遵守操作者给出的重点与约束。

### 3.1 调研方式

优先阅读高价值信息源：

- `README*`、根目录清单文件、工作区配置、锁文件
- 构建、测试、代码检查、格式化、类型检查、代码生成相关配置
- CI 工作流、pre-commit / 任务运行器配置
- 现有指令文件（`AGENTS.md`、`CONTEXTS.md`、`.cursor/rules/`、`.cursorrules`）

读完配置与文档后仍不清楚整体架构时，查看少量代表性代码文件，找出真实入口、包边界与执行流程。
优先读能说明系统整体串联逻辑的文件，不随意翻看底层零散文件。

优先采信**可执行的真实源文件**，而非纯文字文档。文档与配置/脚本冲突时，以可执行源文件为准，
仅保留可验证的内容。

### 3.2 需要提取的内容

提取 Agent 在本仓库工作时最高价值的关键信息：

- 精确的开发者命令，尤其是不容易直观想到的命令
- 如何运行单个测试、单个包、局部验证步骤
- 有强制顺序要求的命令（如 `lint -> typecheck -> test`）
- 单体多包仓库边界、核心目录归属、真实应用/库入口
- 框架/工具链特殊行为：生成代码、数据库迁移、构建产物、特殊环境变量加载逻辑、开发服务器、
  部署流程
- 本仓库独有的编码风格与工作流约定（和框架默认行为不一样的部分）
- 测试特殊点：fixture、集成测试前置依赖、快照处理流程、依赖的外部服务、不稳定或耗时长的套件
- 现有指令文件中值得保留的重要约束

一份质量好的 `AGENTS.md`，内容通常是需要通读多个文件才能推导出来的隐性上下文。

### 3.3 提问规则

仅当仓库本身无法解答关键信息时才向操作者提问；一次最多一批简短问题。适合提问的场景：

- 没有文档记录的团队内部约定
- 分支 / PR / 版本发布相关要求
- 已知但没有书面记录的环境搭建、测试前置条件

仓库已写清楚的内容不重复提问。

### 3.4 编写规则

只包含高价值、本仓库专属指引：

- Agent 很容易猜错的精确命令与快捷操作
- 仅看文件名无法得知的架构说明
- 不同于语言/框架默认行为的约定
- 环境搭建要求、环境特殊行为、运行时坑点
- 重要的现有指令文件引用

优先使用简短章节 + 项目符号列表。仓库简单则文件保持简洁；仓库庞大则只总结真正改变
Agent 工作方式的核心架构事实。

已存在 `AGENTS.md` 时，在原文件基础上迭代优化，不盲目全盘重写：保留经过验证的有效指引，
删除冗余、过时内容，使其与当前代码库保持一致。

### 3.5 需要排除的内容

- 通用软件开发常识
- 长篇教程、完整目录树罗列
- 语言本身显而易见的通用规范
- 猜测性内容、无法验证的描述

拿不准要不要写，就直接省略。
