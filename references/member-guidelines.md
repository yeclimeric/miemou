# 成员规则原文（六套内置规则）

miemou 团队成员不依赖外部 skill 安装与在线获取——六套规则的原文纳入本文件，
派发时按角色与任务性质引用对应章节。末节「全员行为准则」是每个子 agent prompt 的必带件。

## 目录

1. karpathy 四原则（编码行为准则）
2. ponytail：最简完整改动

## 1. karpathy 四原则（编码行为准则）

> 行为准则，减少 LLM 常见编码失误。与项目专属指令合并使用。
> 取舍：这些准则偏向谨慎而非速度。琐碎任务自行判断。

### 1.1 三思而后写（Think Before Coding）

**不臆测。不藏混淆。呈现取舍。**

实现之前：

- 显式陈述你的假设；不确定就问。
- 存在多种解读时全部呈现——不要默默挑一个。
- 存在更简单的做法时说出来，该反驳就反驳。
- 有不清楚的地方就停下，指明困惑点，提问。

### 1.2 简单优先（Simplicity First）

**解决问题的最少代码。不做任何投机性设计。**

- 不做超出要求的功能。
- 单次使用的代码不做抽象。
- 不做没人要求的"灵活性"与"可配置性"。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而 50 行就够时，重写。

自问："资深工程师会说这过度复杂吗？"会，就简化。

### 1.3 外科手术式改动（Surgical Changes）

**只动必须动的。只清理自己制造的残留。**

编辑既有代码时：

- 不"改进"邻近的代码、注释、格式。
- 不重构没坏的东西。
- 遵循既有风格，即使你会用别的写法。
- 注意到无关死代码时提一句——不要删。

你的改动产生孤儿时：

- 删除**因你的改动**而不再使用的 import / 变量 / 函数。
- 不删既有死代码，除非被要求。

检验标准：每一行改动都能直接追溯到用户的请求。

### 1.4 目标驱动执行（Goal-Driven Execution）

**先定义成功标准，循环到验证通过。**

把任务转成可验证的目标：

- "加校验" → "为非法输入写测试，然后让它们通过"
- "修 bug" → "写一个能复现它的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步任务先列简短计划：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
```

强的成功标准让你能独立循环；弱的标准（"让它能跑"）会不断需要澄清。

**准则生效的标志**：diff 里没有多余改动；不再因过度复杂返工；澄清问题出现在实现之前而非犯错之后。

## 2. ponytail：最简完整改动

> 懒资深开发者模式。最好的代码是从未写下的代码。用最少的新代码解决整个问题。

动笔之前：读任务与其触碰的代码，列出改动必须到达的每一处（调用方、测试、fixture、配置、导出）；
检查改动会弄坏什么（会破坏或暴露的数据、会失效的调用方）。这是范围。额外的功能不是。

最小完整改动的取舍顺序，取第一个完全可行的：

1. 它需要存在吗？跳过没人要求的功能、选项与灵活性，并用一行点名跳过了什么。
2. 本代码库已有（helper、组件、服务、模式）？按周围代码的用法用它。
3. 标准库或平台特性？用它，除非项目自有实现（自有组件优先于原生控件）。
4. 已安装的依赖？用它。绝不为几行代码引入新依赖。
5. 能写成一眼看懂的一行吗？一行。
6. 否则：能工作的最少代码。

- 对方案要懒，对改动本身绝不懒：任务需要触达的每一部分（调用方、测试、fixture）都要完成。
- 没人要求的抽象、包装、类型转换、选项、配置、样板、"以后会用"的代码：一律不写。
  删除胜于新增。保持代码库既有的分层、接口与惯例。
- 弄清全部触达面之后，最短的可工作 diff 获胜；需要解码的一行不算短。
- 只注释代码本身说不清的"为什么"，一行。
- 修 bug：动笔前先 grep 受影响函数的每个调用方，然后在共享代码里一次性修根因。
- 移动或合并的代码保留其错误处理与校验。
- 同等大小的选项里，选边界情况正确的那个。
- 懒代码没有检查就不算完成：新的非平凡逻辑（分支、循环、解析器、金额或安全、全新脚本或应用）
  留一个小测试或基于断言的自检；琐碎改动不需要。
- 有已知局限的捷径写成注释：`shortcut: <局限>, <何时升级>`。

**绝不削减**：信任边界的校验、防止数据丢失的错误处理、安全、可访问性、真实硬件所需的标定、
用户明确要求的一切。

## 3. TDD：红-绿-重构

> 团队要求测试先行或编写集成测试时使用。

1. **红**：先写一个会失败的最小测试，精确断言尚未实现的行为；跑一次，确认它因**正确的原因**失败
   （不是语法错、不是环境错、不是测试自身写错）。
2. **绿**：用最简单的实现让测试通过——允许丑，不允许超范围。禁止顺手实现测试没要求的功能。
3. **重构**：在全绿保护下清理重复与坏味道；每步小改、每步跑测试，变红立即回退。

纪律：

- 一个循环只处理一个行为；测试名描述行为，不描述方法调用序列。
- 每个测试都必须能以"实现写错就变红"的方式失败；不为凑覆盖率写断言空气的测试。
- 存量代码缺测试时：先补表征测试（characterization test，锁定当前行为）再重构。

## 4. 诊断循环：困难 bug 与性能回退

> 用户报告功能异常、抛异常、运行缓慢或明确要求诊断时使用。只有在显式说明理由时才可跳过阶段。

### Phase 1：搭反馈回路（这一步就是技能本体）

其余阶段都是机械的。有一个**紧的**红绿信号（能在这个 bug 上变红的信号），就能找到根因。

在反馈回路上花不成比例的精力。按大致顺序尝试：失败测试 → curl/HTTP 脚本 → CLI 调用对比快照 → 无头浏览器脚本 → 回放捕获的 trace → 一次性 harness（最小子系统+mock）→ 属性/模糊循环 → bisect harness（自动化"启动到状态 X、检查、重复"）→ 新旧版本差分 → HITL 脚本（最后手段）。

回路建成后**收紧**它：更快（缓存、跳过无关初始化、缩小测试范围）、信号更尖锐（断言具体症状而非
"没崩"）、更确定（固定时间、种子、隔离文件系统）。30 秒的 flaky 回路几乎等于没有；2 秒的确定性
回路是调试超能力。

非确定性 bug：目标不是干净复现而是**提高复现率**——循环触发 100 次、并行、加压、缩时间窗。
50% 的 flake 可调试，1% 不可调试。

完成判据：能说出**一条命令**（脚本路径、测试调用、curl），已经**跑过至少一次**，它
红能力具备（驱动真实 bug 代码路径并断言用户的**确切症状**）、确定性、秒级、可无人值守运行。
在它存在之前读代码建理论 = 这个技能要防止的那个失败。没有能红的命令，不进 Phase 2。

### Phase 2：复现 + 最小化

跑回路，看它变红。确认失败模式是**用户描述的那个**（错的 bug = 错的修复），多轮可复现。
然后逐项删减（输入、调用方、配置、数据、步骤，一次删一项，每删一项重跑），缩到**仍会变红的最小场景**，
使每个保留元素都是承重的——删掉任何一个都会变绿。最小复现既缩小假设空间，也是 Phase 5 的回归测试。

### Phase 3：提出假设

测试任何假设之前，先产出 **3-5 个排序过的假设**（单假设会锚死在第一个貌似合理的想法上）。
每个假设必须**可证伪**："如果 X 是根因，那么改 Y 会让 bug 消失 / 改 Z 会让它更糟。"
说不出预测的假设是玄学，丢弃或磨尖。排序清单先呈报操作者再测试（操作者常有领域知识能瞬间重排）。

### Phase 4：插桩验证

每个探针对应 Phase 3 的一个具体预测，**一次只改一个变量**。工具优先级：调试器/REPL（一个断点胜过
十条日志）> 区分假设边界处的定向日志 > 永不"全量打日志再 grep"。调试日志打唯一前缀标签
（如 `[DEBUG-a4f2]`），收尾一次 grep 清干净。性能回退：日志通常是错的——先建基线测量
（计时 harness、profiler、查询计划），再 bisect。先测量，后修复。

### Phase 5：修复 + 回归测试

先写回归测试再修，但仅当存在**正确的接缝**（测试能以真实发生方式驱动 bug 模式）。接缝太浅会给出
虚假信心；不存在正确接缝本身就是发现——记录它。存在时：最小复现转失败测试 → 看它失败 → 修复 →
看它通过 → 用 Phase 1 回路对原始（未最小化的）场景再跑一遍。

### Phase 6：清理

原始复现不再复现；回归测试通过（或接缝缺失已记录）；`[DEBUG-...]` 插桩全部移除（grep 前缀）；
一次性原型删除；被证实的那个假设写进 commit message，让下一个调试者直接学到。

## 5. 审视法：对方案与决策的高压质询

> 用于压测计划、设计或决策；架构师出方案后、操作者拍板前使用。

把决策空间建模为**设计树**：每个决策分出挂在它下面的后续决策。按**轮次**推进：每轮提出
**前沿**（前置已定的全部问题——现在就能问、不用猜没听过的答案），每题编号并给出推荐答案，
等问题都答完再算下一轮。措辞让"是"即接受推荐答案。

查**事实**是 agent 的活，永远不推给操作者：前沿问题需要环境事实（文件系统、工具）时，派子 agent
去查；不因它阻塞——除它下游的问题外，前沿照常问。**决策**归操作者：逐个呈上并等待。

进行中的发现沉淀：给深化后的模块起的概念名不在术语表里就补进术语表；术语被磨尖就当场更新；
操作者以承重理由否决候选时，提议记录 ADR（只在未来的探索者确实需要它避免重提同一个方案时才记）。

完成的判据：前沿清空——设计树每个分支都走到，没有任何东西被默默假设。操作者确认达成共识前不动手。

## 6. 架构深化：代码库优化机会扫描

> 用于架构优化、模块接口改进、可测试性提升。与审视法（§5）串联：先扫出候选，再逐个 grill。

先定范围（YAGNI）：操作者点名方向就照做；否则从代码现状判断——入口、最大最纠缠的模块、
其余代码依赖最重的模块、摩擦可感的模块。只基于项目当前状态，不翻 git 历史。

带着摩擦感勘察，记录：

- 理解一个概念要在多个小模块间来回跳的位置
- **浅模块**：接口几乎和实现一样复杂
- 为可测试性抽出纯函数、但真 bug 藏在调用方式里的位置（无**局部性**）
- 紧耦合模块跨越接缝互相泄漏的位置
- 未测试、或通过当前接口很难测试的部分

对任何疑似浅的东西做**删除测试**：删掉它，复杂度是**集中**了还是只是**挪了个位置**？
"集中"才是想要的信号。产出候选清单（涉及文件、问题、方案、收益、建议强度：强 / 值得探索 /
投机），呈报操作者选择，**不先提出接口**。选中的候选用 §5 的审视法走决策树。

## 7. 全员行为准则（每个派发 prompt 必带）

1. 动手前先读项目约定卡与涉及文件的现状；不确定就问，不猜。多种解读并存时全部呈现，不默默挑一个。
2. 简单优先：用解决问题的最少代码；不做超出任务范围的功能、抽象、配置化。写多了问自己"资深工程师
   会不会说这过度复杂"。
3. 外科手术式改动：只动必须动的；不顺手"改进"邻近代码；你的改动产生的孤儿（不再使用的
   import/变量/函数）由你清理，既有死代码只提不删。每行改动可追溯到任务需求。
4. 目标驱动：先定"怎么算完成"（可验证的成功标准），实现到验证通过为止；多步工作先列
   「步骤 → 验证」计划。
5. 新代码带一个能失败的自检（小测试或断言）；非平凡逻辑（分支、循环、解析、金额/安全）必须有
   一个小测试或基于断言的自检，琐碎改动除外。
