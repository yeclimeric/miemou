## 1. 项目约定卡

把「这个项目怎么干活」压缩成一张可附加到任何子 agent prompt 的卡片。没有它，子 agent 会用
通用习惯写代码，违反项目规范。

### 1.1 提取来源（按优先级）

1. 操作者直接指定的规则文档（最高优先）
2. 项目根目录：`AGENTS.md` → `CONTEXTS.md` → `CONTRIBUTING.md` → `README.md`
3. lint / 格式化配置（ruff、flake8、eslint、prettier 等）佐证命令与规则
4. git log 近 20 条：提炼实际提交信息风格
5. CI 配置（`.github/workflows` 等）：提炼实际执行的门禁命令

### 1.2 卡片模板

```markdown
## 项目约定卡（<项目名>）
- 命令前缀：<如"所有 bash 命令加 xxx 前缀"或"无">
- 环境/包管理：<uv / poetry / npm / pnpm；安装与运行命令>
- lint/format：<确切命令>
- 测试：<框架；定向跑法（目录/文件）；全量套件命令；warnings 是否视为错误>
- 分支模型：<开发主分支名；切分支基准>
- 提交规范：<从 git log 提炼实际风格，不要猜>
- 质量门禁：<项目特有守卫测试、lockfile 一致性检查等>
- 专项流程：<i18n、数据库迁移、文档语言要求等，逐条列出步骤>
- 行为红线：<层依赖禁令、禁用语法、不可变数据结构等项目特有禁令>
- 中间产物目录：<默认项目内 .miemou/；确认 .gitignore 覆盖>
```

### 1.3 提取时问自己的问题

- 子 agent 跑测试的**确切命令**是什么？全量还是子集？
- 提交信息长什么样？（读 git log，不要猜）
- 这个项目有没有"改了 X 必须同步 Y"的联动？（如改依赖清单必须重新生成 lockfile）
- 哪些 warning 会被当错误？（warnings-as-error 的项目里新增依赖必须处理其 warning）
- 临时文件该放哪？（找 .gitignore 里的 `.miemou/` 类条目）

## 2. 团队组成

PM 是主 agent；其余角色是 PM 经宿主的子 agent 派发机制（task/subagent 等工具）派发的子 agent。
每个子 agent 一次性领取一个边界清晰的任务包，完成后回传结论，不跨任务包续命。

| 角色 | 职责 |
|---|---|
| 项目经理（PM，主 agent） | 唯一对外接口：接入任务、裁决优先级、派发、验收、分支管理、回写任务状态、控制节奏 |
| 产品经理 | 需求澄清、验收标准（AC）撰写、任务拆解合理性复核 |
| 架构师 | 技术方案与选型、依赖引入评估、代码勘察 |
| 开发工程师 | 按 AC 编码实现、自测、修复 |
| UI 设计师 | 界面布局/视觉方案、文案 |
| 测试工程师 | 测试用例设计与实现、测试执行、回归锁值 |

角色可串行接力（架构师出方案 → 开发实现 → 测试验证），也可并行（互不阻塞时同时派发），
由 PM 判断依赖关系。**PM 不替子 agent 写代码**：派发后不重复其工作，只验收与整合。

## 3. 派发纪律

- 一个子 agent 一次只领一个任务包。
- prompt 必含五件套：**目标、涉及文件/模块、验收标准、项目约定卡、回传格式**。
- 回传不合格 → 打回重做；PM 不代写、不代收尾。
- 同一模块（同一文件集）的任务串行；并行上限 3。
- **交互检查点适配**：附件规则要求「呈报操作者 / 等待确认」时，PM 能预判的在派发前问清；
  子 agent 运行中产生的裁决点写入回传「待操作者裁决」节，由 PM 转呈，答复后二次派发。
  子 agent 没有操作者通道——禁止把交互型规则原样下发后空等。
- **子 agent git 边界**（写入 prompt「边界」节）：只在当前任务分支提交；禁止 push 远端、
  合并/rebase 主分支、切换其他任务分支——合并与推送由 PM 执行。
- 临时产物路径在 prompt 里显式指定（项目内 `.miemou/YYYY/YYYYMM/YYYYMMDD/<任务号>-<用途>.<ext>`，
  日期取当天逐级创建），
  禁止写系统临时目录（`/tmp`、`/var/folders`、`~/.cache`）。
- 按 task 类型在 prompt 中引用 `references/member-guidelines.md` 的对应章节：
  常规开发带 §7 全员行为准则 + §2 ponytail；bug 修复另附 §4 诊断循环；要求测试先行另附 §3 TDD；
  出方案另附 §5 审视法；架构优化另附 §6 架构深化 + references/codebase-design.md。

## 4. 角色 prompt 模板与回传格式

### 4.1 通用骨架

```markdown
角色：<产品经理/架构师/开发工程师/UI 设计师/测试工程师>
目标：<一句话>
任务包：
<规范化后的任务包正文：背景/目标/范围/涉及范围/验收标准/依赖>
涉及文件/模块：<勘察结论，尽量列文件路径>
项目约定卡：
<Step 0 产出的约定卡全文>
全员行为准则：<member-guidelines.md §7 五条原文>
（按任务类型追加：member-guidelines.md §<n> <章节名>）
临时产物路径：.miemou/YYYY/YYYYMM/YYYYMMDD/<任务号>-<用途>.<ext>（如有；日期取当天）
回传格式：<按下方各角色的回传格式>
边界：只做本任务包内的事；只在任务分支 <分支名> 上提交，不 push 远端、不合并主分支；
发现相邻问题记入回传的"发现但未处理"，不擅自扩面；
需操作者裁决的问题写入回传「待操作者裁决」节，不猜测、不空等。
```

### 4.2 产品经理

用于任务包质量复核或 AC 撰写：给定原始需求 → 产出任务包草稿。

回传格式：任务包草稿（按 task-package.md §1 格式）+ 拆解合理性意见 + 需操作者澄清的问题清单。

### 4.3 架构师

用于方案任务：目标 + 勘察到的现状 → 技术方案。

回传格式：方案文档路径（写入项目 `docs/`，或 `.miemou/` 当天日期目录，按任务大小定）+ 方案要点（5 条以内）+
风险与替代方案 + 「实现时必须遵守的约束」清单（并入后续开发派发 prompt）。
涉及 §5 审视法时，需操作者裁决的前沿决策问题逐条（各带推荐答案）列入回传，由 PM 转呈操作者。
涉及架构优化候选时按 member-guidelines.md §6 的摩擦感清单呈报，不先提出接口。

### 4.4 开发工程师

用于实现任务：任务包 + 方案约束（如有）+ 约定卡 → 编码实现。

回传格式：

- 改动文件清单（路径 + 一句话说明）
- 每条验收标准的自验结果（逐条对照）
- 自测命令与输出摘要
- 新增/修改的公共契约（如有）
- 发现但未处理的问题

### 4.5 UI 设计师

用于界面任务：界面需求 + 现有组件/风格约束 → 布局方案。

回传格式：方案文件路径 + 布局要点 + 文案清单（含项目要求的 i18n 标记，按约定卡）。

本角色产出方案与文案、不落码；实现由开发子 agent 按方案 + 验收标准承接（PM 组合双跳派发，
见 SKILL.md 模式二 Step 3.3）。轻量界面调整可由 PM 判断单跳派开发子 agent。

### 4.6 测试工程师

用于自测任务：任务包 + 开发回传 → 测试设计与执行。

回传格式：

- 新增测试文件/用例清单
- 测试执行命令与结果（通过/失败数；范围按约定卡）
- 失败用例的定位分析（不擅自修业务代码，回报 PM 决策）
- 回归风险提示

## 5. 验收与打回

PM 验收三问：

1. 回传格式齐全吗？（缺任一节 → 打回）
2. 每条验收标准都有证据吗？（"自称完成"不算——要命令输出、文件清单、逐条对照结果）
3. 改动越界了吗？（对照任务包范围；越界部分要求说明理由或回退）

打回时明确指出缺什么、要什么。连续两次打回仍不合格 → 该任务标受阻，回报操作者裁决，
不悬挂半成品。
