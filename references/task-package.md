## 1. 统一任务包格式

任何来源的任务，进入排期前都规范化为：

| 字段 | 必填 | 说明 |
|---|---|---|
| id | ✅ | 来源内唯一：文件条目号 / issue 号 / 对话序号（T1、T2…） |
| 标题 | ✅ | 「模块/领域：动作 + 交付物」，≤40 字，祈使动词开头 |
| 类型 | ✅ | Task（明确交付单元）/ Bug（行为与预期不符）/ Feature（新能力提案） |
| 优先级 | ✅ | Urgent / High / Medium / Low |
| 背景 | ✅ | 为什么做：缺口在哪、谁受益、依据什么 |
| 目标 | ✅ | 做完之后系统有什么不同，一句话 |
| 范围 | ✅ | 做：交付物清单；不做：明确排除项（防范围蔓延） |
| 涉及范围 | ✅ | 文件/模块级涉及面（可由 PM 勘察后补齐） |
| 验收标准 | ✅ | 可验证条件清单（含 lint/测试要求） |
| 依赖 | ✅ | 上游任务 id；无则写「独立」 |

## 2. 标题与正文骨架

标题：`模块/领域：动作 + 交付物`——全角冒号分隔；不带类型前缀（类型由「类型」字段承载）；
不以文件路径开头（路径放「涉及范围」）。

| 合格 | 不合格 | 病因 |
|---|---|---|
| `GLM 诊断：阈值分级 + 侧栏卡片` | `【Task】GLM 诊断阈值分级` | 类型前缀冗余 |
| `事件标记：自定义规则引擎 + 导入导出` | `core/events.py：自定义规则引擎` | 以路径开头 |
| `脑网络：图论指标计算 + 拓扑可视化` | `脑网络图论指标计算` | 无领域分隔，无法按域聚合 |
| `静默退出：后台线程未 join 导致崩溃` | `修复bug` | 无信息量、无领域 |

命名动词用祈使开头：实现 / 补齐 / 修复 / 收敛 / 拆分 / 对齐 / 梳理。

按类型选正文骨架（小节标题固定，可空不可删，确无内容写「无」）：

- **Task**：背景 / 目标 / 范围（做、不做）/ 涉及范围 / 验收标准 / 依赖与关系
- **Bug**：现象 / 复现步骤 / 环境 / 影响范围 / 根因（未定位写排查方向）/ 修复方案 / 验收标准
- **Feature**：背景 / 现状 / 目标 / 方案要点 / 替代方案与取舍 / 涉及范围 / 验收标准 / 依赖与关系

## 3. 优先级裁决

| 档 | 语义 |
|---|---|
| Urgent | 阻塞主线，必须本周期解决 |
| High | 关键路径，下一周期内做 |
| Medium | 独立可交付，可并行 |
| Low | 依赖未就绪，延后 |

裁决顺序：**操作者明示 > 一切**（点名做的任务直接置顶）→ 阻塞项（被其他任务以前置门禁引用、
不解决会导致返工的）→ 关键路径（主链上的第一批交付单元）→ 独立可交付（无前置、低风险：
测试补齐、文档等）→ 延后项（依赖未就绪、跨域大件）。

裁决四问（每个候选任务都回答）：

- 它的前置任务都完成了吗？（没完成的先做前置）
- 它阻塞了几个后续任务？（阻塞多的优先）
- 它在本期关键路径上吗？
- 它能独立合并、不与在途任务冲突吗？

## 4. 来源 A：Markdown 任务清单

操作者给一个 `.md` 文件路径（或目录）。解析规则：

- 顶层 `## 章节` 视为能力域分组（仅归类，不参与优先级）
- `- [ ]` / 有序列表条目视为候选任务；`- [x]` 为已完成，跳过
- 条目内 `**加粗**` 后的正文、缩进子列表视为范围/验收标准线索
- 条目缺优先级时按裁决四问推断，推断不出默认 Medium
- 操作者给的是目录：先列出其中所有 `.md` 及条目数呈报，请操作者指定用哪个

回写规则：任务完成后回写该文件——勾选 `- [x]`，并在条目下追加一行
`> 完成（YYYY-MM-DD）：一句话交付摘要`。**禁止重排或删改其他条目。**

## 5. 来源 B：对话直接下达

操作者在对话里口头下达（「这轮做 X 和 Y」）。处理：

1. PM 即时把每个任务规范化为任务包；缺字段向操作者补问（可批量一次问完）。
2. 落一份会话任务台账到项目内 `.tmp/miemou-queue-<日期>.md`（正文骨架格式），
   作为本轮队列呈报与回写的载体。
3. 完成回报即结项；台账同步勾选。

操作者只说了一个任务 → 队列就是它，仍需确认涉及面与验收标准后再开工。

## 6. 来源 C：GitHub Issues

操作者指定某 GitHub 仓库的 issues 作为来源时：

```bash
gh issue list --state open --json number,title,body,labels,milestone
gh issue view <n> --comments   # 看开工占位评论，防重复开工
```

- Issue 的原生字段（Type / Priority / Milestone）直接映射任务包字段；缺 Priority 用裁决四问推断。
- 状态流转用 issue 评论：开工评论「开工：分支 <name>，预计涉及 <模块>」；完成评论附改动摘要与
  自测结果，合并后关闭 issue；部分交付不关闭，评论勾选已完成项、列剩余项。
- 禁止：开工前不评论就改代码；未完成合并就提前关闭；用评论代替 commit message 记录技术细节。
- 多个 open issue 时仍按裁决出 1-3 个的当期队列，不全量开工。

## 7. 来源 D：其他结构化来源

表格 / JSON / CSV / 需求文档等：

1. 先识别行（或对象、章节）到任务的映射：一行一任务？一节一任务？
2. 按 §1 格式逐字段映射；映射不上的字段原文并入「背景」保留。
3. 拆分粒度：一个来源条目含多个交付物时，先按交付单元拆；拆不动则整体入包并标 Low。
4. 映射结果（任务包清单）先呈报操作者核对，再进排期。

## 8. 缺字段补齐规则

- 缺验收标准 → PM 起草后**经操作者确认**才开工（AC 是验收依据，不能 PM 单方面定）。
- 缺涉及范围 → 派勘察类子 agent 或 PM 勘察后补齐；派发前必须检查与在途任务的文件重叠。
- 缺依赖信息 → 默认「独立」。
- 缺背景/目标 → 问操作者；操作者也说不清 → 标 Low 延后，说明原因，不硬做。
