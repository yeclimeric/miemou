# 深模块设计词汇（codebase-design）

> miemou §6 架构深化的配套词汇与指南，完整迁移自 codebase-design skill。
> 全程精确使用本文件术语：不替换成"组件""服务""API""边界"。

设计**深模块**：小接口后面藏大量行为，放在干净的接缝上，通过该接口可测试。
凡在设计或重构代码处，使用这套语言与这些原则。目标：给调用方杠杆、给维护者局部性、
给所有人可测试性。

## 1. 词汇表

精确使用这些术语：不替换成"组件""服务""API""边界"。语言一致就是全部意义。

**模块（module）**：任何有接口和实现的东西。刻意与规模无关：函数、类、包、跨层切片。
_避免_：单元、组件、服务。

**接口（interface）**：调用方要正确使用模块必须知道的一切：类型签名，以及不变量、顺序约束、
错误模式、必需配置、性能特征。_避免_：API、签名（太窄，只指类型层面的表面）。

**实现（implementation）**：模块内部的东西，代码本体。区别于**适配器**：一个东西可以是
小适配器 + 大实现（Postgres 仓库），也可以是大适配器 + 小实现（内存 fake）。话题是接缝时
用"适配器"，否则用"实现"。

**深度（depth）**：接口处的杠杆。调用方（或测试）每学一个单位的接口，能驱动多少行为。
**深**模块 = 小接口后面坐着大量行为；**浅**模块 = 接口几乎和实现一样复杂。

**接缝（seam）**（Michael Feathers）：不改那个位置的代码就能改变行为的地方；模块接口
所在的*位置*。接缝放哪是独立的设计决策，区别于接缝后面放什么。_避免_：边界
（与 DDD 限界上下文撞词）。

**适配器（adapter）**：在接缝处满足一个接口的具体事物。描述*角色*（填哪个槽），不描述
实体（里面是什么）。

**杠杆（leverage）**：调用方从深度得到的东西。每学一个单位接口获得更多能力。
一份实现摊到 N 个调用点和 M 个测试上回本。

**局部性（locality）**：维护者从深度得到的东西。改动、bug、知识与验证集中在一处，
而不是摊到所有调用方。修一次，处处修好。

## 2. 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   小接口            │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│   深实现            │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 薄实现（要避免）：

```
┌─────────────────────────────────┐
│       大接口                     │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  薄实现                          │  ← 只是穿透传递
└─────────────────────────────────┘
```

设计接口时自问：

- 方法数能减吗？
- 参数能简化吗？
- 还能往里多藏复杂度吗？

## 3. 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小、可 mock、可替换的部分组成；
  只是它们不属于接口。模块可以有**内部接缝**（实现私有、自己的测试用）与接口处的
  **外部接缝**。
- **删除测试。** 想象删掉这个模块。复杂度消失 → 它是穿透层。复杂度在 N 个调用方身上重现
  → 它在挣自己的饭钱。
- **接口即测试面。** 调用方和测试跨同一个接缝。想测到接口*后面*去，模块形状多半错了。
- **一个适配器 = 假想接缝。两个适配器 = 真接缝。** 没有东西真的跨它变化，就不引入接缝。

## 4. 为可测试性设计

好接口让测试自然：

1. **接受依赖，不创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积小。** 方法更少 = 需要的测试更少。参数更少 = 测试构造更简单。

## 5. 关系

- **模块**恰有一个**接口**（呈现给调用方与测试的表面）。
- **深度**是**模块**的属性，相对其**接口**度量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**坐在**接缝**上，满足**接口**。
- **深度**给调用方产出**杠杆**，给维护者产出**局部性**。

## 6. 被否决的表述

- **深度 = 实现行数 / 接口行数**（Ousterhout 的比值说）：奖励往实现里注水。我们用"深度即杠杆"。
- **接口 = TypeScript `interface` 关键字或类公有方法**：太窄。这里的接口包括调用方必须
  知道的每个事实。
- **边界**：与 DDD 限界上下文撞词。说**接缝**或**接口**。

## 7. 深化指南

在依赖给定的情况下，如何安全地深化一簇浅模块。假定上文词汇：模块、接口、接缝、适配器。

### 7.1 依赖分类

评估深化候选时，先分类它的依赖。类别决定深化后的模块如何跨接缝测试。

1. **进程内**：纯计算、内存状态、无 I/O。永远可深化：合并模块，直接通过新接口测试。
   不需要适配器。
2. **本地可替换**：依赖有本地测试替身（PGLite 替 Postgres、内存文件系统）。替身存在即可
   深化。深化后的模块带着替身在测试套件里跑。接缝是内部的；模块外部接口不开端口。
3. **远程但自有（端口与适配器）**：跨网络边界的自有服务（微服务、内部 API）。在接缝处定义
   **端口**（接口）。深模块持有逻辑；传输层作为**适配器**注入。测试用内存适配器，生产用
   HTTP/gRPC/队列适配器。建议的形状："在接缝处定义端口，生产实现 HTTP 适配器、测试实现
   内存适配器，让逻辑集中在一个深模块里，尽管它跨网络部署。"
4. **真外部（Mock）**：不可控的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖
   作为注入的端口；测试提供 mock 适配器。

### 7.2 接缝纪律

- **一个适配器 = 假想接缝，两个 = 真接缝。** 除非至少两个适配器站得住（通常是生产 + 测试），
  不引入端口。单适配器接缝只是间接层。
- **内部接缝 vs 外部接缝。** 深模块可以有内部接缝（实现私有、自己的测试用）与接口处的
  外部接缝。不因测试用了内部接缝就把它暴露到接口上。

### 7.3 测试策略：替换，不叠加

- 深化模块的接口上有了测试之后，浅模块上的旧单测变成废料；删掉。
- 在深化模块的接口上写新测试。**接口即测试面**。
- 测试断言接口上的可观察结果，不断言内部状态。
- 测试应活过内部重构：它们描述行为，不描述实现。实现一改测试就得改，说明它测过了接口。

## 8. 设计两次

操作者想为选定的深化候选探索替代接口时，用这个并行子 agent 模式。源自 Ousterhout 的
"Design It Twice"：你的第一个想法不太可能是最好的。使用上文词汇：模块、接口、接缝、
适配器、杠杆。

### 8.1 框定问题空间

派子 agent 之前，为选定候选写一份面向操作者的问题空间说明：

- 任何新接口都要满足的约束
- 它依赖的依赖及其分类（§7.1）
- 一个粗略示意性的代码草图，把约束落具体——不是提案，只是让约束可见

呈给操作者，随即进下一步。子 agent 并行工作时操作者正好读和想。

### 8.2 派子 agent

并行派 3 个以上子 agent，每个全新上下文，必须产出**截然不同**的接口。

每个子 agent 一份独立技术简报（文件路径、耦合细节、依赖分类、接缝后面是什么），与第一步
面向操作者的说明无关。给每个子 agent 不同的设计约束：

- 子 agent 1："接口最小化：入口点最多 1-3 个。每个入口点杠杆最大化。"
- 子 agent 2："灵活性最大化：支持很多用例与扩展。"
- 子 agent 3："为最常见调用方优化：默认场景做到平凡简单。"
- 子 agent 4（如适用）："围绕端口与适配器设计跨接缝依赖。"

简报同时包含本文件词汇表与 `GLOSSARY.md` 词汇，让每个子 agent 的命名与架构语言、
领域语言一致。每个子 agent 产出：

1. 接口（类型、方法、参数，外加不变量、顺序、错误模式）
2. 用法示例：调用方怎么用
3. 接缝后面藏了什么实现
4. 依赖策略与适配器（§7.1）
5. 取舍：杠杆在哪里高、哪里薄

### 8.3 呈现与对比

依次呈现各设计让操作者消化，然后用文字对比。按**深度**（接口处的杠杆）、**局部性**
（改动集中在哪里）、**接缝位置**对比。

对比后给出自己的推荐：你认为哪个最强、为什么。不同设计的元素能组合好就提议混合。
要有立场：操作者要的是强烈的判断，不是菜单。
